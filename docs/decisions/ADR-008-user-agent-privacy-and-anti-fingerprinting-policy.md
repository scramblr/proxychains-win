# ADR-008: User-Agent Privacy and Anti-Fingerprinting Policy (Hybrid Strategy)

## Status
Accepted

## Date
2026-09-07

## Context
In proxy and tunneling clients, fingerprinting vectors pose significant risks to user anonymity. When an application tunnels traffic or establishes intermediate proxies, two primary transport patterns exist:
1. **SOCKS5 Protocols:** Pure binary framing (`05 01 00 ...`) over local loopback (`127.0.0.1:9050`) to the Tor daemon. Zero application-layer HTTP headers are emitted by the proxy engine itself during proxy handshake.
2. **HTTP CONNECT Proxies:** The tunneling engine emits an explicit `CONNECT <host>:<port> HTTP/1.1` request. Historically, upstream implementations transmitted static identifying headers such as `User-Agent: proxychains\r\n`, which immediately unmasked the client to upstream proxy operators and network observers as an automated or non-standard client.

### Evaluation of User-Agent Randomization
A common naive proposal is to randomize the User-Agent header across a rotating pool of browser strings. However, security research into browser fingerprinting (notably documented by the Tor Project and in privacy analyses such as *"Tor's Bold Move: Why Removing User-Agent Randomization Unlocks a New Era of Browser Anonymity"*) demonstrates that User-Agent randomization actually degrades privacy due to the **"Mask-Mismatch" problem**:
- Rotating user-agent strings (e.g., claiming to be Safari on macOS, then Edge on Windows, then Chrome on Android) directly contradict the invariant characteristics of the client's underlying TCP/IP stack (TTL, TCP window size), TLS fingerprint (JA3/JA4 cipher suites, extensions), and runtime behavior.
- Every misalignment between the claimed User-Agent mask and lower-layer protocol characteristics produces a unique, high-entropy fingerprint that isolates the user rather than concealing them.
- In privacy engineering, **uniformity is power**: the strongest protection is blending indistinguishably into a large, identical crowd.

## Decision
proxychains-win adopts a deterministic **Hybrid User-Agent Strategy**:

1. **Tor Chains (Strict Uniformity Enforced):**
   - For all connections routed through the local Tor daemon (`127.0.0.1:9050` or `127.0.0.1:9150`), proxychains-win strictly enforces the canonical Tor Browser User-Agent:
     `Mozilla/5.0 (Windows NT 6.1; rv:60.0) Gecko/20100101 Firefox/60.0`
   - Under no circumstances is User-Agent randomization permitted for Tor traffic. The non-Tor user-agent list is never loaded or executed for Tor connections.
   - This guarantees that any HTTP CONNECT proxy handshakes match the canonical Tor crowd signature identically.

2. **Non-Tor HTTP Proxy Chains (Configurable Pool):**
   - When non-Tor HTTP proxies are configured, operators may configure a specific modern browser User-Agent or select from a curated list of top browser User-Agents via `http_user_agent` or `user_agent` directives in `proxychains.conf`.
   - The default configuration file provides a commented-out list of top browser strings with explicit documentation warning against arbitrary rotation.
   - If no custom User-Agent is specified for a non-Tor chain, the engine falls back safely to the canonical Tor Browser User-Agent.

3. **Total Purge of Identifying Strings:**
   - The legacy `User-Agent: proxychains` signature is permanently removed from the codebase.
   - No tracking cookies, dynamic domain generation routines, predictable ephemeral headers, or identifiable markers are generated by the proxy engine.

## Consequences
- Prevents mask-mismatch fingerprinting across the Tor network.
- Eliminates upstream proxy unmasking caused by identifiable proxychains client headers.
- Guarantees deterministic, reproducible behavior without random entropy leakage.
